WP Forensics & Recovery Assistant

Browser Demo — the project's own Python engine, running locally in your browser

Local processing only. Your backup ZIP is read inside your own browser using WebAssembly (Pyodide). No backup, PHP source, file path, or scan result is ever uploaded to a server. The only network requests this page makes are to download the public Pyodide and JSZip libraries, and later to fetch official WordPress.org core checksums (a version number only, never your files).

Download Report

Reports are generated in your browser and saved straight to your device. The HTML report is a download only — it is never opened automatically and never inserted into this page. Evidence from sensitive files (wp-config.php, .env, *.pem, *.key, id_rsa, names containing "credentials", and *.sql) is always redacted.

Core Integrity Verification Partial — browser based

The archive is extracted into a temporary in-memory directory, the official checksums for the detected WordPress version and locale are fetched by your browser from api.wordpress.org, and the extracted files are compared with the upstream core_verify.verify_core() implementation. Only the version, the locale, and the official checksum list ever leave your browser — no file, path, or hash is sent anywhere.

Partial verification. Only files that appear in the official WordPress.org checksum set are compared. Plugins, themes, uploads, wp-content, and any other file outside that set are not checked. A result without mismatches is therefore not a proof that the installation is free of injected code.

⚠️ Browser-Specific Limitations

  • Runs entirely in your browser via Pyodide; no files are uploaded to any server.
  • The first load downloads the Pyodide runtime (tens of megabytes) and may take around 30 seconds.
  • Large archives can exceed browser memory limits; use the command-line tool for very large backups.
  • Only ZIP archives you explicitly select can be analysed — the demo cannot read a local directory.
  • Snapshot comparison needs two ZIP archives; both are read into the in-memory filesystem, compared by path and SHA-256 hash, and deleted afterwards.
  • Files that could not be hashed in one of the two snapshots are reported as limitations instead of being classified as added or removed.
  • Symlink detection is stricter than upstream: the upstream is_symlink() helper matches only the exact mode 0o120000, so this demo also applies the standard S_IFLNK type-bit mask and rejects symlinks that carry ordinary permission bits.
  • Findings are indicators that require manual review. A clean scan does not prove a site is free of malware.
  • Core integrity verification is partial and browser based. It compares only the files listed in the official WordPress.org checksum set for the detected version and locale; every other file in the archive is ignored, and a version that WordPress.org does not publish checksums for cannot be verified at all.
  • Core verification needs network access to api.wordpress.org. The request sends the version and locale only, never file names, hashes, or file contents, and the comparison itself runs locally.

All analysis performed locally in your browser.
